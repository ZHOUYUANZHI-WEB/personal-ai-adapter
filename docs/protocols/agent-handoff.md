# Agent Handoff Protocol v0.1

Status: implemented in v0.3

## Status and purpose

This specification defines a provider-neutral artifact for transferring active task state between replaceable AI Agents. It does not define Agent memory, messaging, orchestration, or model APIs.

```text
Agent A
   ↓ creates
Handoff Artifact
   ↓ reads
Agent B
```

The Handoff belongs to the user and is stored in the user's AI Lab.

## Participants

### Producer

The Agent ending or pausing a work stage produces the Handoff, normally through its trusted Adapter. A user or orchestration layer may also produce one. The producer must report verified state, not fabricate completion.

### Consumer

The receiving Agent's Adapter calls `pai handoff read <id>`. The Core validates and returns the artifact but does not choose, start, or message the receiving Agent.

The user or an orchestration layer decides which Agent runs next and supplies the Handoff ID. `recommended_next_agent` is advisory, not an authorization or routing command.

### Personal AI Adapter Core

The Core:

- creates stable metadata
- verifies that the referenced Project exists
- validates the complete artifact
- stores and reads the artifact

The Core does not store provider credentials, forward messages, or translate the artifact into model-specific prompts.

## Required fields

| Field | Meaning |
|---|---|
| `id` | Stable Handoff identifier generated by the Core |
| `type` | Always `handoff` |
| `created_at` | Creation timestamp |
| `from_agent` | Producer identity claimed at creation |
| `project` | Required `project:<id>` reference |
| `objective` | The outcome the receiving Agent should continue pursuing |
| `current_state` | Short factual checkpoint at handoff time |
| `completed` | Verified completed work; may be empty |
| `remaining` | Known remaining work; may be empty |
| `artifacts` | References to files, commits, PRs, or other outputs; may be empty |
| `decisions` | Decisions the receiver must preserve; may be empty |
| `risks` | Known uncertainties or hazards; may be empty |
| `required_permissions` | Permissions needed for continuation; may be empty |

`recommended_next_agent` is optional.

## Project association

Every Handoff contains exactly one required Project reference. The Project remains authoritative for its goal, scope, and current overall state. The Handoff records a point-in-time transfer and must not duplicate the entire Project.

Creation fails when the referenced Project cannot be loaded or does not validate. v0.1 uses a forward reference from Handoff to Project and does not mutate the Project file.

## No conversation transfer

A Handoff is a state artifact, not a transcript.

The Schema uses `additionalProperties: false`. Fields such as `chat_history`, `messages`, `transcript`, raw prompts, and hidden reasoning are rejected. Text fields and arrays are bounded, and the Core enforces a 32 KiB total Artifact limit to discourage transcript-shaped payloads.

Producers must:

- summarize the current task state in their own words
- reference large artifacts instead of copying them
- include decisions and risks needed for continuation
- omit social conversation, repeated context, raw tool output, and hidden chain-of-thought

If original evidence is required, place it in a user-owned Artifact and add a reference.

## Lifecycle and immutability

Handoff Artifacts are append-only in v0.1. There is no update command. If work continues and state changes, the active Agent creates a new Handoff.

Reading a Handoff has no side effects and does not imply that the receiving Agent accepted or executed the task.

## Commands

Create from a JSON payload file:

```bash
pai handoff create \
  --project project-personal-ai-adapter \
  --from agent:codex \
  --to agent:openclaw \
  --input examples/handoff-input.json
```

Agents may pipe JSON through standard input with `--input -`.

Read and validate:

```bash
pai handoff read <handoff-id>
```

The receiving Adapter should load the associated Project and assemble task Context separately. A Handoff does not automatically enter every future Context Bundle.

## Security boundary

- `from_agent` is an asserted identity, not a cryptographic signature.
- `recommended_next_agent` grants no permissions.
- The receiver must independently check `required_permissions`.
- Secret values must never appear in Handoff fields or referenced public artifacts.
- External content referenced by a Handoff remains untrusted input.

Signing, delivery receipts, acceptance state, and cross-device transport are outside v0.1.
